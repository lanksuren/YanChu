# 言出 · 优化清单

> 和 [问题清单](问题清单.md) 平级，回答的是另一个问题：
> 问题清单记「**哪里坏了**」，这里记「**哪里还能更好**」——没坏，但有明确的收益和明确的量法。
>
> 一条优化项要想登记，必须写得出「怎么量」；量不出来的想法叫愿望，不叫优化。

## 登记规则

1. 编号递增，**永不复用**；不做的写 `close` 并给出结论，不删行。
2. 每条必须有**依据**（实测数字或代码位置）和**判定标准**（跑什么、看哪个指标）。
3. 状态：`open` 未排期 / `doing` 在做 / `verify` 改完待验 / `done` 已验证 / `close` 不做（写原因）。
4. 和问题清单的边界：**会出错、会误导用户的进问题清单**（YC-xxx），**只是慢/只是不够好的进这里**（OP-xxx）。

## 明细

### OP-001 部署时自测线程数，挑最快的固定下来

- **收益** 单次解码耗时最多降 30%；在混合架构（P 核 + E 核）机器上避免踩坑
- **状态** `open`
- **依据** 本机实测（Ultra 5 338H，12 核 12 线程，Qwen3-ASR 0.6B int8）用 `--bench-lat` 扫线程：

  | threads | 固定开销（截距） | 每秒斜率 | 6s 音频单次 |
  |---:|---:|---:|---:|
  | 2 | 187ms | 91ms | 733ms |
  | **4** | **170ms** | **71ms** | **596ms** |
  | 6 | 454ms | 55ms | 784ms |
  | 8 | 703ms | 79ms | 1177ms |

  4 线程最快；6/8 线程截距暴涨，原因是混合架构把线程甩到 E 核，
  每个算子都要等最慢那根线程。**「核越多越快」在这里是错的**，
  所以没有跨机器的对照表可用 —— 只能上机自测。

- **做法** 首次运行（或切换识别模型后）做一次 5 秒左右的标定：
  1. 拿内置的 1 秒 + 6 秒两段样例音频，对 `threads ∈ {2,4,6,8}` 各跑 2 次，取中位数；
  2. 选「耗时不超过最快值 1.15× 的最小线程数」（省电、给别的东西留核）；
  3. 写进 `models/asr.json` 的 `threads`，之后不再变；`YANCHU_ASR_THREADS` 仍可覆盖；
  4. 界面上给一句「已按本机实测选定 4 线程」的说明，别让用户以为是我们拍脑袋。
- **判定标准** 在同为 12 核混合架构的机器上标定结果应为 4；
  标定后 `--bench-lat` 的截距与手工扫参的最优值相差 ≤ 10%；
  冷启动总时长增加 ≤ 5s。
- **关联** `asr.rs`（`thread_count` / `default_threads`）、`bench_lat.rs`（现成的测法）、`models/asr.json`

### OP-002 部署时探测 GPU，有核显/独显就换 DirectML 后端

- **收益** 单次解码 3–5×（本机是 Arc B370 核显 + 24G 共享显存，完全够放 0.6B int8）
- **状态** `open`
- **依据** `--bench-lat` 显示成本大头在 encoder（41ms/秒音频）与 decoder（~10ms/字）的矩阵乘，
  这正是 GPU 擅长的；CPU 侧 4 线程已经压到极限（见 OP-001）。
  障碍是 `sherpa-onnx` 的 Rust crate 只发 CPU 预编译包
  （`target/sherpa-onnx-prebuilt/sherpa-onnx-v2.0.1-win-x64-static-MT-Release-lib`），
  想上 GPU 得自己构建 ONNX Runtime（DirectML EP）+ sherpa-onnx，再用 `SHERPA_ONNX_LIB_DIR` 指过去。
- **做法**
  1. 先用 `dxdiag` / `Win32_VideoController` 探一下有没有可用显卡（本机：Intel Arc B370）；
  2. 做一版 DirectML 构建，跑 `--bench-lat` 对比 CPU 基线；
  3. 跑不动或者精度掉了（DML 对 int8 量化算子支持有限）就退回 CPU，`close` 这条并记原因。
- **判定标准** 6s 音频单次解码 ≤ 200ms（当前 596ms），且 `--bench bench\corpus` 的 CER 不退化超过 0.5 个点。
- **关联** `Cargo.toml`（sherpa-onnx 依赖）、构建脚本 `tools/build.bat`

### OP-003 增量大润色：每句闭合就润，松手只润最后一句

- **收益** 长口述 −1s 以上；把「松手→出字」从润色主导变成 ASR 主导
- **状态** `open`
- **依据** 端到端实测（11.4s 语料，4 次）：松手→出字 P50 907ms 里，
  定稿解码 195ms、**大润色 544ms**、写入 25ms；34s 长口述里大润色 1118ms。
  而大润色耗时随字数线性涨（本机 qwen3.5:2b，`--polish-test` 实测）：

  | 输入字数 | 大润色耗时 |
  |---:|---:|
  | 29 | 564–727ms |
  | 47 | 1240ms |
  | 112 | 1868ms |

- **做法** 每句定稿、拿到小润色结果后，后台对「该句 + 上文」跑一次大润色并缓存；
  松手时只处理最后一句，再把缓存的段落拼起来。产品定义 v2 第四节已经把它写成硬性条件。
- **注意** 单次调用的**地板价约 560ms**（`--llm-ping` 单 token 也要 310ms），
  所以这条对**短句几乎无收益**（短句本来就只有一句），对 100 字以上的口述才值钱。
- **判定标准** 34s 长口述「松手→出字」P50 ≤ 1000ms；11.4s 短口述不退化（≤ 970ms）；
  气泡→落字的措辞一致率（`--dev-report`）不下降。
- **关联** `llm.rs`（`polish`）、`lib.rs`（`finish` / 句子定稿处）、[ASR-延迟优化方案](ASR-延迟优化方案.md)

### OP-004 分点独立成「结构层」，别混在润色里

- **收益** 保住整体分点，同时让 OP-003 的句级缓存不会破坏版式
- **状态** `open`
- **依据** 现在的分点由两处共同产生，职责是混的：
  1. 规则层 `polish::format_enumerations`：按「第一步 / 一个是 / 如果×3」这些稳定标记确定性排版（0ms）；
  2. 大润色提示词里的「原文用第一步/第二步列出的，保持条目数」（`REWRITE_TEMPLATE`、`API_DEEP_TEMPLATE`）。
  实测 47 字输入「第一…第二…第三…」→ 输出 `1. 先把数据库迁移跑完。`，说明分点确实在工作。
  但句级增量缓存之后，每句只能看到自己，判不了「这句话该不该开一个新条目」。
- **做法** 结构判定单独一层，输入是「已经润好的句子数组」而不是原文：
  1. 先走规则：命中序号词（第一/第二/首先/其次/最后）、并列标记（一个是/另一个/还有）、
     条件分支（如果…就…）就开条目；
  2. 规则判不出来、且总字数 ≥ 100 时，再跑一次「只排结构、不许改字」的薄提示词
     （输入已经去掉了口头语，比全量润色短得多，估计 200–400ms，待测）；
  3. 结构层必须在**落字前**完成 —— 不能先落一段再加编号。
- **判定标准** 含「第一/第二/第三」的 100 字语料，输出分点数 = 3，且逐条内容与原文对应；
  普通叙述（无标记）不被误分点；结构层耗时 P95 ≤ 400ms。
- **关联** `polish.rs`（`format_enumerations`）、`llm.rs`（提示词）、`bench/replay`（已有回放语料）

### OP-005 提示词按字数分档，短句用最短指令

- **收益** 短句润色 −100～300ms（待测）
- **状态** `open`
- **依据** 29 字输入的大润色要 564–727ms，而 `--llm-ping`（单 token）是 310ms，
  差值主要花在 prefill + 生成上；标准档提示词有两条规则 + 分隔线，对 30 字的输入明显偏重。
- **做法** 在现有的 `REWRITE_MIN_CHARS = 100` 之外，再加一档「超短句」（< 30 字）：
  只给一句话指令（「只补标点、接碎句，不改字」），提示词文件放 `models/prompts/short.txt`，
  用 `YANCHU_PROMPT_LOCAL` 之外的新变量或自动选择；配合 `--polish-test` 做 A/B。
- **判定标准** 30 字输入的大润色 P50 ≤ 450ms，且措辞一致率不下降。
- **关联** `llm.rs`（`template_for` / `load_prompt`）、`models/prompts/`

### OP-006 短句且规则层已干净时跳过大润色

- **状态** `done` —— 2026-11-04 落地（commit `perf(润色): 短句且规则层已收拾干净时跳过大润色`）
- **实测收益** 端到端（03.wav 11.4s，各 4 次）：松手→出字 **P50 907 → 380ms，P95 970 → 382ms**，
  而且方差几乎归零（376–382ms，润色 2ms）。长口述不受影响（>30 字仍走模型，实测 1772ms）。
- **依据** 单次大润色的地板价约 400–600ms（`--llm-ping` 单 token 也要 310ms），证据是：

  | 观察 | 数据 |
  |---|---|
  | 27 字真实会话，模型输出与规则层**逐字相同** | 连续 7 次，每次 500–600ms |
  | 8 条多样短句，模型改对 | 5 条，全部落在三类：补问号、删句首「这个/那个」、连接词前补逗号 |
  | 8 条多样短句，模型改了等于没改 | 3 条 |

  也就是说短句交给模型，收益只来自三类可枚举的症状，其余是纯等待。

- **做法（和最初设想不同）** 原本想按字数硬切，实测发现字数和收益没关系
  （17 字是 no-op，12 字反而有收益），于是改成**按症状判**：

  ```text
  跳过条件 = 短于 30 字
           且 句尾不是「为什么/怎么样/是不是/吗/呢…」却没问号
           且 不以「这个/那个 + 人称」开头
           且 没有「然后/但是/所以/不过/而且/另外」前不带标点的一口气句
  ```

  三条症状正是实测里模型唯一改对的地方，所以跳过不换质量。开关 `YANCHU_LLM_SETTLED=0`。
- **判定标准** 已有 3 项单测拿 8 条实测样本对拍（`settled_gate_matches_measured_value`）；
  回归看 `--dev-report` 的措辞一致率是否下降。
- **关联** `pipeline.rs`（`settled_enough`）、`llm.rs`

### OP-008 用规则补掉短句的三类症状，让更多句子落到快路径

- **收益** 每覆盖一类症状，就多一批短句从 900ms 掉到 380ms
- **状态** `open`
- **依据** OP-006 的快路径只吃「无症状」的句子；现在这三类症状仍然要走模型：
  1. 句尾疑问词缺问号：「…是为什么。」→ 需要判断题/陈述（「我也不知道为什么」是陈述，不能一律改？）；
  2. 句首「那个/这个 + 人称」：「那个他说明天上线」。现成的 `strip_demonstrative_fillers`
     只认「我/你/咱」，不认「他/她」；连续两个指示词（「这个那个我们」）也只能剥掉一个；
  3. 连接词前补逗号：「跑完然后重启」。规则层只在**已有句号**时降级成逗号（`soften_internal_periods`），
     对完全没有标点的串不补。
- **做法** 一条一条来，每条都要过 `bench/corpus` 的措辞一致率和规则层单测；
  「疑问词→问号」风险最高（会把陈述句改成问句），建议先只做「吗/呢」这种无歧义结尾。
- **判定标准** 短句语料里被快路径接住的比例 ≥ 70%（现在约 3/8）；措辞一致率下降 ≤ 2 个点。
- **关联** `polish.rs`（`strip_demonstrative_fillers` / `soften_internal_periods`）、`pipeline.rs`（`settled_enough`）

### OP-007 换因果流式音频塔（qfuxa/qwen3-asr-0.6b-streaming）

### OP-009 灰字单独一个色阶（别复用正文的 muted）

- **收益** 一眼分清「已定稿的实字」和「还在变、随时会被改写的灰字」
- **状态** `verify` —— 2026-11-04 已改，等真机看体感
- **依据** 用户反馈「黑色的字和灰色的字区别不大」。查下来：气泡里的灰字直接复用
  `--text-muted`（浅色主题 `#5b6472`），在 11px 字号下和正文 `#111827` 只差一档明度；
  而深色主题的 `#9ca3af` 与 `#e5e7eb` 反而更近。
- **做法**
  1. `tokens.css` 新增 `--text-tail`：浅色 `rgba(17, 24, 39, 0.38)`、深色 `rgba(229, 231, 235, 0.42)`；
  2. `bubble.css` 的 `--tail` 改用它，正文/润色中的文字仍用 `--text-muted`（那边要保持可读）。
- **还可以再走一步（未做，先看这次够不够）**
  - 灰字末尾加一根很细的插入符（只在说话时显示），比整体变色更能说明「还在变」；
  - 灰字用 `font-weight: 400` + 正文 `500` 做字重区分（现在是同字重，只靠颜色）。
  两条都会引入新的动效/布局变化，先不加。
- **判定标准** 一眼扫过去能分出「哪半句已经定型」；控制面板里把字号调到最小（10px）也分得出。
- **关联** `app/src/tokens.css`（`--text-tail`）、`app/src/bubble.css`（`--tail`）

### OP-010 指示器电平：自适应增益 + 状态滞回

- **收益** 说话时环能看出起伏（不再长期顶格）；句尾换气不再让指示器在「呼吸」和「放大」之间来回跳
- **状态** `verify` —— 2026-11-04 已改，等真机连说一段确认
- **依据** 两个独立问题，都出在「用绝对值 + 单拍判决」：
  1. **顶格**：`indicator.js` 里是 `sqrt(min(1, level * 5))`。本机语料 RMS 实测 0.052（-25.7dBFS），
     乘 5 就是 0.26 → 0.51，还算正常；但麦克风一开 AGC、或说话离得近，RMS 到 0.2 就顶到 1，
     之后不管怎么大声都是满格 —— 也就是用户说的「始终处于最大振幅」。
  2. **突跳**：`level_loop` 是 `if level > 0.01 { speaking } else { silent }`，
     单拍判决、无滞回。换气、轻声尾字、词间停顿都会在 0.01 上下抖，
     指示器跟着每 60ms 在两种视觉状态间切换（静音态还挂着 `breathe` 动画，切换时动画重播）。
- **做法**
  1. **状态机加滞回 + 最短停留**（`LevelGate`）：开口 0.010 要连续 3 拍（180ms），
     停下 0.005 要连续 8 拍（480ms）—— 480ms 正好跨过正常换气停顿；
     中途任何一拍超过出口阈值就把「停下」计数清零。
  2. **电平改名次而非绝对值**（`indicator.js`）：用最近峰值做归一化
     （`peak` 取 max，按 0.995/拍 衰减 ≈ 8 秒半衰），`unit = level / (peak * 1.2)`，
     再 `^0.75` 软压缩。峰值只到 0.83 满，常态说话落在 0.6–0.8，留着可见行程。
  3. **动画缓冲**：包络上升 0.45 / 回落 0.12（≈3 拍升、≈0.5 秒收）；
     `#ring`/`#core` 的状态类过渡从 80ms 拉到 220ms；`breathe` 幅度从 0.72 收到 0.86、周期 1.8s→2.4s。
- **判定标准** 连着说 20 秒带正常换气：环的 scale 在 1.0–1.45 之间连续变化，
  不出现长时间贴 1.55；句尾 500ms 内不发生 `silent ↔ speaking` 来回切换；
  单测 `level_tests` 5 项通过。
- **关联** `app/src-tauri/src/lib.rs`（`level_loop` / `LevelGate`）、`app/src/indicator.js`、`app/src/indicator.css`
